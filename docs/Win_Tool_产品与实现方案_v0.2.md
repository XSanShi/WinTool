## 1. 背景、目标与非目标

### 1.1 背景〔事实〕

用户要一个 Windows 桌面小工具，只做三件事：**待办事项、账号密码记录、随笔**。参考过两个项目：

| 参考项目 | 形态 | 与我们的关系 |
| --- | --- | --- |
| TO-DO Panel（Electron 44，`docs/TO-DO-Panel_逆向分析_v1.0.md`） | 屏幕顶部"刘海"条，六页面 | 只作反面参照：功能过多；顶部"留海"是用户明确不要的形态 |
| PaperTodo（.NET 10 WPF，`docs/PaperTodo_逆向分析_v1.0.md`） | 桌面纸片 + 折叠贴边胶囊 | 正面参照：贴边小悬浮球的成熟实现、原子写与托盘/热键骨架 |

### 1.2 产品目标〔事实〕

1. 三类功能，一屏可达，不引入项目管理层级。
2. 不带屏幕中间"留海"式 UI。
3. 待办完成后**不自动消失**（用户改为手动清理），但要能落成本地 Markdown 留底。
4. 唤起路径短：主窗口 ⇄ 贴边小悬浮球。

### 1.3 非目标

- 不做云同步、账号体系、多人协作。
- 不做 AI 提醒、剪贴板历史、链接收藏、屏幕录制、音乐组件、多工作流（详见 §2.2）。
- 不做插件系统、不做 MCP 接口、不做脚本执行器。
- 不做跨平台；只面向 Windows。

## 3. 界面布局与隐藏 / 唤出

### 3.1 硬约束

1. **不得出现屏幕中间（含顶部居中、视口居中）的"留海"式悬浮条**〔用户确认〕。
2. 主界面是**常规可缩放窗口**，有标题栏与最小化/关闭〔拟议〕。
3. 隐藏后必须变成**贴屏幕边缘的小悬浮球**，点击球可重新唤出〔用户确认〕。
4. 悬浮球不得遮挡任务栏与系统托盘可点击区域〔拟议·未确认，见 D3b〕。

### 3.2 主窗口布局〔拟议·未确认〕

```
┌───────────────────────────────────────────────────────────┐
│  Win_Tool                                        ─  □  ✕  │ ← 系统标题栏
├──────────┬──────────────────────────────┬─────────────────┤
│ 待办     │  列表区                       │  详情 / 编辑区   │
│ 账号密码 │  （按当前分区渲染）           │  （选中项的字段）│
│ 随笔     │                              │                 │
├──────────┴──────────────────────────────┴─────────────────┤
│ 状态栏：条数 / 上次保存时间 / 留底目录快捷入口            │
└───────────────────────────────────────────────────────────┘
```

- 初始尺寸〔拟议·未确认〕：960 × 620 逻辑像素，最小 720 × 480。
- 左侧导航固定三项，不提供"更多"入口——这是范围内只有三类功能的可视化表达。
- 详情区随分区切换内容；不做弹窗层级（参考项目与 PaperTodo 都靠多窗口/多层级，我们不学）。
- 不使用 WebView 承载界面（技术细节见 §8）。

### 3.3 隐藏形态：贴边小悬浮球〔用户确认 + 待确认项〕

**已确认**〔用户确认，m00220〕：
- 点击隐藏后，主窗口消失，屏幕边缘出现一个**小悬浮球**。
- 点击该球可再次唤出（回到主窗口）。

**未确认参数**（下表参数格一律"待确认"，禁止填入拟议数值后当作实现依据）：

| 参数 | 状态 | 影响面 |
| --- | --- | --- |
| 球的直径 / 宽高 | 待确认 | 命中区域、遮挡范围、图标可辨识度 |
| 贴哪条边（左/右/上次位置/固定角） | 待确认 | 多屏算法、拖拽是否需要 |
| 垂直位置（居中/可拖动/记忆） | 待确认 | 是否引入位置持久化字段 |
| 是否允许拖动球换边 | 待确认 | 是否要 hit-test 拖动 + 位置落盘 |
| 是否显示未完成待办数（角标） | 待确认 | 是否需要常驻计数刷新 |
| 是否置顶（TopMost） | 待确认 | 与全屏应用/游戏/演示模式的交互 |
| 是否允许"始终隐藏、只用快捷键唤出" | 待确认 | 是否提供"无球模式" |
| 隐藏的触发方式（关闭按钮/最小化/快捷键/托盘） | 待确认 | 关闭按钮语义（退出 vs 隐藏） |

**行为规则〔拟议·未确认〕**（结构可先实现，数值与开关等确认）：
- 状态机只三态：`Expanded`（主窗口）/ `Ball`（贴边球）/ `Exited`（进程退出）。不引入 PaperTodo 那种 7×3×8 维度组合。
- 只允许单实例：一个进程、一个球、一个主窗口，第二次启动把已有实例唤出（见 §8.4）。
- 球被点击 → `Expanded`；主窗口隐藏动作 → `Ball`；两者互斥，任何时刻只有一个可见。
- 关闭主窗口**不得**退出进程，除非用户显式选择退出（托盘菜单/设置项）。
- 球与主窗口共享同一份内存数据，不产生"两份状态"。

对照参考：PaperTodo 用 `EdgeCapsuleSlotState` 等三组正交枚举 + 意图 reducer 管贴边胶囊（`EdgeCapsuleModel.cs:3-136`），我们只借"reducer 收口"的思想，不借它的维度数量〔推断〕。

### 3.4 界面层不做的事

- 不做屏幕顶部的形变条（TO-DO Panel 的 `islandWindow`，`main.js:889`）。
- 不做透明无边框的"贴顶悬浮条"。
- 不做悬停展开的预览卡片（PaperTodo 的 EdgeCapsulePreview）。
- 不把悬浮球做成"可收起的一列胶囊"。

### 4.2 目录结构〔拟议·未确认，路径取决于 D7〕

```

  todos.json              # 待办条目
  notes/                  # 随笔：一篇一文件（见 §7.4，D5 待确认）
  vault.bin               # 账号密码（格式取决于 D1a，见 §6.2）
  archive/                # 待办 Markdown 留底（见 §5.5，D2a/D2b 待确认）
```

### 4.3 三类数据的关系

- 三类**互不引用**：待办条目不知道随笔，账号密码不知道待办。参考项目把待办与正文塞进同一个 `PaperData`（`Models.cs:586-652`），我们不采用——三类功能各自独立更利于"精简"。
- 唯一交叉点是"待办 → Markdown 留底"的单向写出，且写出后不再读回（归档只读）。

### 4.4 落盘可靠性要求（无参数，仅机制）

以下为**机制约束**，不含可调数值，可直接实现〔拟议·未确认〕：

1. **原子写**：写同目录临时文件 → `flush to disk` → 原子替换目标；失败重试并清理残留临时文件。参考实现：PaperTodo `DurableAtomicFileWriter.cs:73-155`（`.tmp` + `FileShare.None` + `Flush(flushToDisk:true)` + `File.Move(overwrite:true)` + 5 次 100 ms 重试）。
2. **写入去抖 + 强制上限**：编辑后延迟落盘，并设一个"无论怎么打字都必须落盘"的上限。参考：PaperTodo 1 s 去抖 + 10 s 上限（`AppController.cs:180-199`）。
3. **崩溃残留清理**：启动时清理 `*.tmp` 残留并记录。
4. **外部改动检测**：只对"显式导入/恢复"路径做源文件哈希比对，普通自动保存不比对（避免用户手动编辑文件后被覆盖）。参考：`StateStore.WriteSafety.cs:51-79`。
5. **写入停机信号**：进程退出时置位，禁止新的写入排队（`PersistenceWriteLifetime`，同文件 :93-107）。
6. **备份**：仅保留机制（"定期生成一份可回滚快照"），**份数与间隔待确认**（D7 附属项），不在此处填数值。

## 5. 待办事项

### 5.1 字段〔拟议·未确认〕

```jsonc
// todos.json 条目
{
  "id": "uuid",             // 稳定标识，留底去重依赖它
  "text": "string",         // 单行标题
  "done": false,
  "createdAt": "ISO8601",
  "completedAt": "ISO8601 | null",   // D2 改为手动清理后，完成时间成为留底的必要字段
  "order": 0,
  "archivedAt": "ISO8601 | null"     // 已写入留底的时间；null = 尚未留底
}
```

字段说明：
- `completedAt` 是**新增必要字段**：v0.1 假设"完成即清理"，清理时机由程序掌握；D2 改为手动清理后，必须自己记录完成时刻，否则无法决定留底内容的时间归属〔推断〕。
- `order` 维持连续整数（参考 PaperTodo `TodoRules.NormalizeOrders`，`TodoRules.cs:46-52`）。
- 不设 `deadline`：是否需要截止时间/提醒见 D4，未确认前不入模型。

### 5.2 新增流程

1. 列表底部（或顶部"+"）聚焦输入框，回车即建一条。
2. 输入为空或纯空白 → 不建条目（参考 PaperTodo `IsPlaceholder` 语义，`TodoRules.cs:9-24`）。
3. 新建条目落在未完成区末尾，`done=false`、`completedAt=null`、`archivedAt=null`。
4. 立即触发去抖落盘。

### 5.3 完成流程

1. 勾选 → `done=true`、`completedAt=now`。
2. **条目保留在原位置或移到已完成区**〔待确认（D8-1）〕；两个选项都要能实现，先按"保留位置 + 视觉区分"实现亦可，但必须由用户裁决后定稿。
3. 触发留底判定（见 §5.5，触发点本身待确认）。
4. 触发落盘。
5. 取消勾选 → `done=false`；`completedAt` 是否清空**待确认（D2a 附属）**（影响留底去重口径）。

### 5.4 手动清理（D2 已确认：不自动清理）

**已确认**〔用户确认，m00220〕：完成项**不由程序自动移除**，清理动作交给用户。

未确认的子问题：

| 编号 | 问题 | 状态 |
| --- | --- | --- |
| D2-1 | 清理粒度：逐条删除 / "一键清理全部已完成" / 两者都有 | 待确认 |
| D2-2 | 清理是否需要二次确认 | 待确认 |
| D2-3 | 清理是否进入撤销（撤销时长） | 待确认 |
| D2-4 | 删除**未完成**条目是否也走同一入口 | 待确认 |

**实现必须满足的不变式（无参数）**〔拟议·未确认，属机制层〕：

> **写先于删**：任何已完成条目从 `todos.json` 移除之前，其留底记录必须已经成功落盘（含 `flush`）。留底失败时**禁止删除**，并向用户显示可见错误。

此不变式替代 v0.1 的"完成即清理"链路，是 D2 改动后唯一不可协商的技术约束〔推断：由"要留底"+"手动删"共同推出〕。

### 5.5 Markdown 留底规则

**已确认**：需要本地 Markdown 留底〔事实，m00001 约束〕
**已确认**：清理由用户手动执行〔用户确认，m00220〕
**未确认**：留底的**触发点**、文件位置、命名、历史保留策略

| 编号 | 问题 | 状态 | 说明 |
| --- | --- | --- | --- |
| D2a | 触发点：勾选完成即写 / 用户点"清理"时批量写 / 两者 | 待确认 | 直接决定"删除前该条是否已有留底" |
| D2b | 留底文件位置（数据目录内 / 用户文档目录 / 用户自选） | 待确认 | — |
| D2c | 文件组织：单文件追加 / 按天分文件 / 按次清理分文件 | 待确认 | — |
| D2d | 是否保留完整历史（只增不删） | 待确认 | — |
| D2e | 条目被取消完成后再完成，是否产生第二条留底 | 待确认 | 与 `completedAt` 清空口径绑定 |
| D2f | 留底文件是否允许用户直接编辑（编辑后是否影响去重） | 待确认 | 影响是否需要校验和/索引 |

**与 D2a 无关的格式规则〔拟议·未确认，可先实现〕**：

- 复选语法：完成项 `- [x] 文本`，未完成项（若某方案也要写）`- [ ] 文本`。
- 续行缩进 4 空格（多行文本）。
- 转义集合（照抄 PaperTodo `TodoClipboardFormatter.cs:9-89`）：``\ ` * _ { } [ ] < > ~ | &``；行首为 `#` `>` `+` `-` 时额外转义；形如 `1.` / `1)` 后接空白的序号分隔符也转义。
- 每条留底附带元信息（完成时间、原条目 id），用于幂等判定；元信息的具体写法随 D2c/D2f 定稿。
- 写入使用 §4.4 的原子写机制。

**被阻塞的下游项**（D2a/D2b/D2c 未定前不得开工）：
- 留底文件名与目录常量
- 清理按钮的确认文案（是否需要提示"已留底 N 条"）
- 备份目录是否要包含 `archive/`

### 5.6 异常与边界

| 场景 | 处理〔拟议·未确认〕 |
| --- | --- |
| 留底写入失败（磁盘满/占用/权限） | 中止删除，保留条目，状态栏显示错误，提供重试 |
| `todos.json` 损坏 | 从备份恢复；恢复失败则进"只读保护"模式，禁止写入，导出原始文件 |

| 条目文本含 `\r\n` 混用 | 归一化为 `\n` 后再序列化 |

## 6. 账号密码

### 6.1 记录字段〔拟议·未确认〕

| 字段 | 必需 | 说明 |

| `id` | 是 | 稳定标识 |

| `username` | 否 | — |
| `password` | 是（本功能存在的理由） | 复制时走剪贴板，是否需要"定时清空剪贴板"见 D8-4 |
| `url` | 否 | 只存文本，不自动打开（避免引入浏览器依赖） |
| `notes` | 否 | 备注/二级验证恢复码等 |
| `createdAt` / `updatedAt` | 是 | — |

不设字段：分类、标签、密码强度评分、历史密码版本（均在范围外）。

### 6.2 存储与保护（D1 部分已确认）

**已确认**〔用户确认，m00220〕：账号密码**保存在本地**（不联网、不上云）。

**仍待确认**（下表为候选，不是已定实现）：

| 编号 | 问题 | 候选 | 状态 |
| --- | --- | --- | --- |
| D1a | 保护方式 | (a) 系统凭据保护（Windows DPAPI，绑定当前用户)；(b) 主密码派生密钥加密（可跨机迁移）；(c) 明文（仅当用户明确选择） | 待确认 |
| D1b | 是否需要跨机迁移/备份可解密 | 与 D1a 强相关：DPAPI 方案换机不可解密 | 待确认 |
| D1c | 是否要求"打开即用、不输密码" | 与 D1a/D1b 冲突项，需一次裁决 | 待确认 |
| D1d | 复制密码后是否自动清空剪贴板（及延时时长） | — | 待确认 |

**在 D1a 确认前，以下一律不得写入代码**：vault 文件二进制格式、密钥派生参数、是否引入主密码 UI、错误提示文案（"解密失败"vs"未设置主密码"）。

**可先行实现的部分（与 D1a 无关）**〔拟议·未确认〕：
- 内存中的记录模型（§6.1）与增删改查 UI。
- 存储层抽象接口（`Load()/Save()`），实现留空待 D1a 落地。
- 敏感值不写日志、不进异常消息、不在界面上明文回显 password 字段。

**参考实现事实**（只作可行性证据，不作选型依据）：
- TO-DO Panel：`credentials.vault.json` 存 `{payload: base64(safeStorage.encryptString(JSON))}`，Windows 下即 DPAPI，整库单 blob，无主密码（`docs/TO-DO-Panel_逆向分析_v1.0.md` §账号密码）。
- PaperTodo：**没有**账号密码功能，无可参考实现（`docs/PaperTodo_逆向分析_v1.0.md` §9）。

### 6.3 能力边界（不承诺）

- 不承诺抗内存取证：解密后明文存在于进程内存。
- 不承诺抗同用户权限下的恶意程序（DPAPI 方案的信任边界就是登录会话）。
- 不做密码强度校验、不联网校验泄露。

## 8. 拟议技术选型（建议，非已确认选择）

### 8.1 候选与适用条件

| 候选 | 适用条件 | 代价 | 证据 |
| --- | --- | --- | --- |
| **.NET 8/10 + WPF**（推荐候选） | 只需 Windows；需要贴边悬浮球、置顶、托盘、全局热键、DPI 精确控制；接受 C# | 团队需会 XAML/C#；UI 迭代比 Web 慢 | PaperTodo 用 .NET 10 WPF 实现同类形态（126,831 行），证明可行〔事实〕 |
| Tauri 2（Rust + WebView2） | 想要 Web UI 的开发效率 + 小体积；愿意写 Rust 胶水做 Win32 | 悬浮球/置顶/多屏要自己写 Win32 绑定；WebView2 运行时依赖 | — |
| Electron | 团队是前端栈；不在乎体积与内存 | 包体大、内存高；透明窗+点击穿透需额外处理 | TO-DO Panel 用 Electron 44，靠 650 ms watchdog 与 60 ms 轮询解决穿透（`main.js` 常量段）〔事实〕 |
| Flutter Desktop | 未来要跨平台 | Windows 端贴边/托盘生态较弱 | — |

**推荐结论**〔拟议·未确认，D6〕：优先 **.NET 8（LTS）+ WPF**，理由是三类功能全是"本地文件 + 原生窗口小工具"，最大技术风险在**贴边悬浮球与 DPI/多屏**，而这一层在 WPF 里是原生能力、在 Web 壳里都要绕 Win32。若团队没有 C# 能力，则退到 Tauri 2。

> 论文依据：PaperTodo 的 ADR 曾尝试用 Swift 重写 macOS 壳，最终因"原生壳只覆盖折叠态、主界面是 12,900 行渲染层"而回退到单一技术栈（TO-DO Panel `docs/adr/0001`）——**教训是"别为一个小形态引入双栈"**，对我们是选型反向约束〔事实 + 推断〕。

### 8.2 与选型无关的共性技术点〔拟议·未确认〕

1. **单实例**：互斥量 + 命名管道把第二实例的参数转交首实例（参考 PaperTodo `SingleInstanceHelper.cs`）。
2. **托盘**：托盘图标常驻，双击唤出主窗口；右键菜单含"显示主窗口 / 设置 / 退出"。WPF 可用 `Hardcodet.NotifyIcon.Wpf`（PaperTodo 用其分叉）。
3. **全局热键**：注册一个唤出热键，需处理"已被占用"（`ERROR_HOTKEY_ALREADY_REGISTERED`）并给出可见提示；具体组合键待确认（D3c）。
4. **开机自启**：写 `HKCU\...\Explorer\StartupApproved\Run` 而非裸写 `Run` 键（参考 `SystemSettingsHelper.cs:9-63`）；是否默认开启待确认（D7）。
5. **禁止事项**：不使用 `alwaysOnTop + 屏幕顶部形变` 组合（即 TO-DO Panel 的岛形态）；不使用 DirectComposition 合成队列（PaperTodo 为多胶囊才需要）。

### 8.3 明确不引入的依赖

- 不引入数据库（SQLite/LMDB）：条目量级小，JSON + 原子写足够；图片类需求在范围外（PaperTodo 用 LMDB 存图片，我们不做）。
- 不引入 WebView2 作为主界面载体。
- 不引入 ORM、不引入 IPC 框架。

### 8.4 进程模型

单进程、单 UI 线程、后台仅一个落盘任务。任何"每 N 毫秒轮询鼠标位置"的逻辑都只在"悬浮球可见"时启用（参考 TO-DO Panel 60 ms 轮询的代价教训）〔推断〕。
