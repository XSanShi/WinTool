## 1. 背景、目标与非目标

### 1.1 背景〔事实〕

用户要一个 Windows 桌面小工具，只做三件事：**待办事项、账号密码记录、随笔**。参考过两个项目：

| 参考项目 | 形态 | 与我们的关系 |
| --- | --- | --- |
| TO-DO Panel（Electron 44，`docs/TO-DO-Panel_逆向分析_v1.0.md`） | 屏幕顶部"刘海"条，六页面 | 只作反面参照：功能过多；顶部"留海"是用户明确不要的形态 |
| PaperTodo（.NET 10 WPF，`docs/PaperTodo_逆向分析_v1.0.md`） | 桌面纸片 + 折叠贴边胶囊 | 正面参照：贴边小悬浮球的成熟实现、原子写与托盘/热键骨架 |

### 1.2 产品目标〔事实〕

1. 三类功能，一屏可达，不引入项目管理层级。
2. 不带屏幕中间"留海"式 UI。
3. 待办完成后**不自动消失**（用户改为手动清理），但要能落成本地 Markdown 留底。
4. 唤起路径短：主窗口 ⇄ 贴边小悬浮球。

### 1.3 非目标

- 不做云同步、账号体系、多人协作。
- 不做 AI 提醒、剪贴板历史、链接收藏、屏幕录制、音乐组件、多工作流（详见 §2.2）。
- 不做插件系统、不做 MCP 接口、不做脚本执行器。
- 不做跨平台；只面向 Windows。

## 3. 界面布局与隐藏 / 唤出

### 3.1 硬约束

1. **不得出现屏幕中间（含顶部居中、视口居中）的"留海"式悬浮条**〔用户确认〕。
2. 主界面是**常规可缩放窗口**，有标题栏与最小化/关闭〔拟议〕。
3. 隐藏后必须变成**贴屏幕边缘的小悬浮球**，点击球可重新唤出〔用户确认〕。
4. 悬浮球不得遮挡任务栏与系统托盘可点击区域〔拟议·未确认，见 D3b〕。

### 3.2 主窗口布局〔拟议·未确认〕

```
┌───────────────────────────────────────────────────────────┐
│  Win_Tool                                        ─  □  ✕  │ ← 系统标题栏
├──────────┬──────────────────────────────┬─────────────────┤
│ 待办     │  列表区                       │  详情 / 编辑区   │
│ 账号密码 │  （按当前分区渲染）           │  （选中项的字段）│
│ 随笔     │                              │                 │
├──────────┴──────────────────────────────┴─────────────────┤
│ 状态栏：条数 / 上次保存时间 / 留底目录快捷入口            │
└───────────────────────────────────────────────────────────┘
```

- 初始尺寸〔拟议·未确认〕：960 × 620 逻辑像素，最小 720 × 480。
- 左侧导航固定三项，不提供"更多"入口——这是范围内只有三类功能的可视化表达。
- 详情区随分区切换内容；不做弹窗层级（参考项目与 PaperTodo 都靠多窗口/多层级，我们不学）。
- 不使用 WebView 承载界面（技术细节见 §8）。

### 3.3 隐藏形态：贴边小悬浮球〔用户确认 + 待确认项〕

**已确认**〔用户确认，m00220〕：
- 点击隐藏后，主窗口消失，屏幕边缘出现一个**小悬浮球**。
- 点击该球可再次唤出（回到主窗口）。

**未确认参数**（下表参数格一律"待确认"，禁止填入拟议数值后当作实现依据）：

| 参数 | 状态 | 影响面 |

| 是否允许"始终隐藏、只用快捷键唤出" | 待确认 | 是否提供"无球模式" |
| 隐藏的触发方式（关闭按钮/最小化/快捷键/托盘） | 待确认 | 关闭按钮语义（退出 vs 隐藏） |

**行为规则〔拟议·未确认〕**（结构可先实现，数值与开关等确认）：
- 状态机只三态：`Expanded`（主窗口）/ `Ball`（贴边球）/ `Exited`（进程退出）。不引入 PaperTodo 那种 7×3×8 维度组合。
- 只允许单实例：一个进程、一个球、一个主窗口，第二次启动把已有实例唤出（见 §8.4）。

- 球与主窗口共享同一份内存数据，不产生"两份状态"。

对照参考：PaperTodo 用 `EdgeCapsuleSlotState` 等三组正交枚举 + 意图 reducer 管贴边胶囊（`EdgeCapsuleModel.cs:3-136`），我们只借"reducer 收口"的思想，不借它的维度数量〔推断〕。

### 3.4 界面层不做的事

- 不做屏幕顶部的形变条（TO-DO Panel 的 `islandWindow`，`main.js:889`）。
- 不做透明无边框的"贴顶悬浮条"。
- 不做悬停展开的预览卡片（PaperTodo 的 EdgeCapsulePreview）。

### 4.3 三类数据的关系

- 三类**互不引用**：待办条目不知道随笔，账号密码不知道待办。参考项目把待办与正文塞进同一个 `PaperData`（`Models.cs:586-652`），我们不采用——三类功能各自独立更利于"精简"。
- 唯一交叉点是"待办 → Markdown 留底"的单向写出，且写出后不再读回（归档只读）。

### 4.4 落盘可靠性要求（无参数，仅机制）

以下为**机制约束**，不含可调数值，可直接实现〔拟议·未确认〕：

1. **原子写**：写同目录临时文件 → `flush to disk` → 原子替换目标；失败重试并清理残留临时文件。参考实现：PaperTodo `DurableAtomicFileWriter.cs:73-155`（`.tmp` + `FileShare.None` + `Flush(flushToDisk:true)` + `File.Move(overwrite:true)` + 5 次 100 ms 重试）。
2. **写入去抖 + 强制上限**：编辑后延迟落盘，并设一个"无论怎么打字都必须落盘"的上限。参考：PaperTodo 1 s 去抖 + 10 s 上限（`AppController.cs:180-199`）。
3. **崩溃残留清理**：启动时清理 `*.tmp` 残留并记录。
4. **外部改动检测**：只对"显式导入/恢复"路径做源文件哈希比对，普通自动保存不比对（避免用户手动编辑文件后被覆盖）。参考：`StateStore.WriteSafety.cs:51-79`。
5. **写入停机信号**：进程退出时置位，禁止新的写入排队（`PersistenceWriteLifetime`，同文件 :93-107）。
6. **备份**：仅保留机制（"定期生成一份可回滚快照"），**份数与间隔待确认**（D7 附属项），不在此处填数值。

## 5. 待办事项

### 5.1 字段〔拟议·未确认〕

```jsonc
// todos.json 条目
{
  "id": "uuid",             // 稳定标识，留底去重依赖它
  "text": "string",         // 单行标题
  "done": false,
  "createdAt": "ISO8601",
  "completedAt": "ISO8601 | null",   // D2 改为手动清理后，完成时间成为留底的必要字段
  "order": 0,
  "archivedAt": "ISO8601 | null"     // 已写入留底的时间；null = 尚未留底
}
```

字段说明：
- `completedAt` 是**新增必要字段**：v0.1 假设"完成即清理"，清理时机由程序掌握；D2 改为手动清理后，必须自己记录完成时刻，否则无法决定留底内容的时间归属〔推断〕。
- `order` 维持连续整数（参考 PaperTodo `TodoRules.NormalizeOrders`，`TodoRules.cs:46-52`）。
- 不设 `deadline`：是否需要截止时间/提醒见 D4，未确认前不入模型。

### 5.2 新增流程

1. 列表底部（或顶部"+"）聚焦输入框，回车即建一条。
2. 输入为空或纯空白 → 不建条目（参考 PaperTodo `IsPlaceholder` 语义，`TodoRules.cs:9-24`）。
3. 新建条目落在未完成区末尾，`done=false`、`completedAt=null`、`archivedAt=null`。
4. 立即触发去抖落盘。

### 5.3 完成流程

1. 勾选 → `done=true`、`completedAt=now`。
2. **条目保留在原位置或移到已完成区**〔待确认（D8-1）〕；两个选项都要能实现，先按"保留位置 + 视觉区分"实现亦可，但必须由用户裁决后定稿。
3. **不触发留底**：留底发生在用户执行清理时（D2a 已确认，见 §5.5），勾选动作本身不写任何 `.md` 文件。
4. 触发落盘（`todos.json`）。
5. 取消勾选 → `done=false`；`completedAt` 是否清空**待确认（D2e 附属）**（影响留底去重口径）。

### 5.4 手动清理（D2 已确认：不自动清理）

**已确认**〔用户确认，m00220〕：完成项**不由程序自动移除**，清理动作交给用户。

未确认的子问题：

| 编号 | 问题 | 状态 |
| --- | --- | --- |
| D2-1 | 清理粒度：逐条删除 / "一键清理全部已完成" / 两者都有 | 待确认 |
| D2-2 | 清理是否需要二次确认 | 待确认 |
| D2-3 | 清理是否进入撤销（撤销时长） | 待确认 |
| D2-4 | 删除**未完成**条目是否也走同一入口 | 待确认 |

**实现必须满足的不变式（无参数）**〔拟议·未确认，属机制层〕：

> **写先于删**：任何已完成条目从 `todos.json` 移除之前，其留底记录必须已经成功落盘（含 `flush`）。留底失败时**禁止删除**，并向用户显示可见错误。

此不变式替代 v0.1 的"完成即清理"链路，是 D2 改动后唯一不可协商的技术约束〔推断：由"要留底"+"手动删"共同推出〕。

#### 5.5.1 「单文件追加」的准确含义（重要，决定实现方式）

"追加"在这里**不是** `FileMode.Append` 往文件尾写字。理由是：真 append 会与 §4.4 的原子写冲突——若进程在写到一半时被杀，文件尾部会留下半行/半条记录，而这个文件正是用户唯一的历史凭据。

因此**追加 = 读改写（copy-on-append）**：

```
读现有留底文件 → 在文本末尾拼接新批次 → 写临时文件 → flush → 原子替换
```

代价是每次清理重写整个文件（O(文件大小)）。以本项目量级（纯文本、每天几条待办）这个代价可以忽略；**但它是 D2d（是否永久保留完整历史）的直接约束**：如果将来 D2d 定为"永久保留且不轮转"，必须重估——这是单文件追加路线的固有代价，不是实现缺陷〔推断〕。

**由单文件追加推出：文件内必须有批次分隔**。否则多次清理的内容混在一起，无法区分批次、无法定位、无法人工核对。因此规定：

- 每次清理写一个 `## <本地时间 yyyy-MM-dd HH:mm>` 段头（时间格式〔拟议〕，可改）。
- 段内是该批次的条目，按清理时的顺序。
- 段与段之间空一行。
- 单文件内**不写文件级头部**（不写"这是自动生成请勿编辑"之类），避免用户改文件时的心理门槛；是否写头部随 D2f。

> 这条策略是从用户的决策直接推出来的，不是新增需求：既然选单文件，就必须让"哪一批"可读。

#### 5.5.2 执行链（可直接编码）

```
用户点击"清理已完成"
  → 取待清理集合 S（S = done=true 的条目；粒度见 D2-1）
  → 若 S 为空：仅提示，不产生任何写入
  → 解析留底目录与文件名（配置项；默认在安装目录下新建目录）
  → 探测：目录存在且可写？文件存在且可写？（不存在则按"将新建"处理）
  → 任一不满足：中止，提示，S 保持原样（一条都不删）
  → 若文件已存在：读取全文 + 记录 (长度, 最后写入时间戳) 作为乐观校验基线
  → 生成新批次文本（段头 + 转义后的条目；含 completedAt 与条目 id）
  → 拼接：旧全文 + 空行 + 新批次
  → 写临时文件（同目录）→ flush to disk → 校验 → 原子替换目标
  → 若替换前发现文件长度/时间戳已变（用户同时编辑了它）：不覆盖，改走"追加到副本"或报冲突
  → 成功：从 todos.json 删除 S → 落盘 todos.json
  → 失败：不删任何条目，保留 S，显示错误 + 重试入口
```

这条链就是 §5.4「写先于删」不变式在"单文件追加"形态下的完整形态。两点必须实现到位：

1. **外部编辑不覆盖**：留底文件是用户可读可改的明文文件，用户很可能一边用编辑器开着它。写回前比对长度/时间戳，变了就**不能**用内存里的旧内容覆盖（否则吞掉用户的手改）。
2. **追加的幂等**：同一批条目重复清理不得写两次（例如用户清理成功后撤销、再清理一次）。判定依据是**文件内是否已存在该条目 id**（在新增批次时扫描文本中的 id 标记），而不是依赖外部索引文件——因为用户可能手改文件，索引必然失配（D2f 未定，此方案对手改友好）。

#### 5.5.3 留底文件必须出现的信息

每条至少包含：`completedAt`、原文（多行完整保留）、原条目 id（供幂等）。推荐呈现**仅为示意，不是已定排版**：

```markdown
## 2026-11-14 18:57

- [x] 买牛奶（19:40 完成，id: 6f2c…）
- [x] 交周报
      第二行续文按 4 空格缩进
```

#### 5.5.4 仍待确认

| 编号 | 问题 | 状态 | 影响的下游 |
| --- | --- | --- | --- |
| D2d | 是否保留完整历史（只增不删、永不清理） | 待确认 | 单文件是否会无限增长、是否需要轮转/归档分包 |
| D2e | 取消完成后再完成、再清理，是否产生第二条留底 | 待确认 | 幂等键取 `id` 还是 `id + completedAt` |
| D2f | 用户直接编辑留底文件是否算受支持行为（影响是否需要 id 可读性、是否加文件头、BOM） | 待确认 | 幂等扫描策略的稳健度 |
| D2b-2 | 默认目录不可写时的回退行为 | 待确认 | 见 §4.2 |

**由于选了单文件追加，D2-3（清理是否可撤销）现在有了强约束**〔拟议·未确认，待 D2-3 裁决〕：若允许撤销，**推荐只把条目放回 `todos.json`，不回滚留底文件**（"文件只增不删"）。理由是回滚需要精确定位并截断上次追加的字节，一旦用户中途编辑过文件就会算错偏移，风险远大于收益；代价是撤销后该条目在留底里"多留一次"，与 D2e 共用同一套幂等判定。

#### 5.5.5 已定格式规则（与 D2d/D2f 无关，可先实现）

- 复选语法：完成项 `- [x] 文本`；若某方案也要写未完成项，用 `- [ ] 文本`。
- 续行缩进 4 空格，保证多行文本不破坏 Markdown 列表结构。
- 转义集合照抄 PaperTodo `TodoClipboardFormatter.cs:9-89`（可直接移植）：反斜杠、反引号、`* _ { } [ ] < > ~ | &`；行首为 `# > + -` 时额外转义；形如 `1.` / `1)` 后接空白的序号分隔符也转义。
- 换行统一为 `\n`；编码 UTF-8。**是否带 BOM 不预设**（影响记事本打开时的中文显示，随 D2f 定稿）。
- 一律走 §4.4 的原子写；**不得**用 `FileMode.Append` 直接追加（见 §5.5.1）。

#### 5.5.6 被阻塞的下游项

- 文件体积上限、轮转策略、分包规则（**D2d 未定前不得开工**，且不得预设任何阈值）
- 清理按钮文案（是否提示"已留底 N 条"——N 的呈现依赖 D2-2）
- 备份目录是否要包含留底目录（D7 附属）

#### 5.5.7 明确不做的

- 不做"完成即自动写 `.md`"（与 D2a 冲突）。
- 不做"程序自动删除或裁剪留底文件"（D2d 未确认前，留底只由用户手动处置）。
- 不做多文件分片（与 D2c 冲突；D2d 若改为"需要轮转"时必须回来改这一条）。
- 不把留底实现成"导出功能"：导出是用户主动选目标文件，留底是清理的副产物，两者入口与失败语义都不同。

## 6. 账号密码

### 6.1 记录字段〔拟议·未确认〕

| 字段 | 必需 | 说明 |
| --- | --- | --- |
| `id` | 是 | 稳定标识 |

| `password` | 是（本功能存在的理由） | 复制时走剪贴板；是否定时清空见 D1d |
| `url` | 否 | 只存文本，不自动打开（避免引入浏览器依赖） |
| `notes` | 否 | 备注 / 二级验证恢复码等 |
| `createdAt` / `updatedAt` | 是 | — |

不设字段：分类、标签、密码强度评分、历史密码版本（均在本工具范围外，见 §2.2）。

### 6.2 存储：本地明文（D1a 已确认）

**已确认的两项**：

| 编号 | 决定 | 来源 |
| --- | --- | --- |
| D1（部分） | 账号密码**保存在本地**，不联网、不上云 | 〔用户确认，m00220〕 |
| D1a | 保护方式 = **明文**（不做加密、不接系统凭据库、无主密码） | 〔用户确认，m00446〕"用明文就可以" |

#### 6.2.1 文件与格式

- 文件：`<数据根>/vault.json`（文件名〔拟议〕），与 `todos.json` 同级。
- 内容：UTF-8 明文 JSON，形如 `{"version":1,"rows":[{"id":…,"title":…,"username":…,"password":…,…}]}`。
- 写入：走 §4.4 的原子写（临时文件 + flush + 原子替换），与待办同一套机制。
- 可读性：目标是**用户能用记事本直接打开、看懂、手改、修坏后自己救回来**。因此不使用 base64、不做字段混淆、不加自定义二进制头。

#### 6.2.2 明文意味着什么（工程事实，不是附带建议）

选定明文后，下面这些是该方案**固有的**事实，必须写进实现与验收里，而不是上线后再发现：

1. **同机同用户身份的任意进程可直接读取该文件**，无需提权。它的实际门槛等于"Windows 登录会话"。
2. **文件是纯文本**，因此会被 Windows Search 索引、会被 OneDrive/网盘类同步工具上传、会被备份软件收录、会被 DLP/录屏/远程协助类软件采集。这些行为由系统与第三方软件决定，本应用无法在文件层面阻止。
3. **进程内存中存在明文**，崩溃转储（dump）、页面文件（pagefile/hiberfil）都可能含明文片段。因此实现上**必须**：不主动生成转储、不实现任何"错误报告上传"、日志与异常消息不得包含字段值。
4. **与替代方案相比换来的好处也是实的**：零加密依赖、无"解密失败/凭据不可用"这类无法自救的故障态、换机直接拷文件即可、用户能自己修数据、排查问题不需要工具。
5. 若将来要改成加密，迁移成本集中在"读明文 → 写密文"的一次性转换上；因此**存储层仍保留 `ICredentialStore` 接口**（`Load()/Save()`），把"格式"关在一个实现里。

#### 6.2.3 因为选了明文，必须做的四件事（可选项都已剔除）

| 事项 | 要求 | 说明 |
| --- | --- | --- |
| 日志脱敏 | 所有日志/异常/调试输出禁止输出 `password`、`username` 与 `notes` 原文 | 实现上给这些字段套 redact 包装，禁止直接 `ToString()` 进日志 |
| 界面遮罩 | `password` 默认以圆点/星号显示，提供"按住或点击显示" | 具体交互〔拟议〕；避免旁人一眼看到 |
| 文件权限（拟议） | 首次创建时把 DACL 收紧为"当前用户 + SYSTEM"，去掉继承的 `Users` 读权限 | 若所在卷/文件系统不支持 ACL（FAT、部分网络盘），**跳过并记录警告，不阻断使用** |
| 目录位置 | 设置页显示 vault 的**完整路径**并提供"打开所在文件夹" | 明文下，用户必须知道文件在哪、长什么样 |

#### 6.2.4 明确不做（因明文而失去意义或与之矛盾）

- 不做主密码、不做密钥派生（PBKDF2/Argon2）、不引 `ProtectedData`/DPAPI、不做加密容器。
- 不做"看起来像加密"的处理（base64、字段位移、简单异或）——这些不改变可读性门槛，只会让用户误以为有保护。
- 不做字段级加密、不做"只加密 password 列"的折中。
- 不做自动上传/同步/云备份。

#### 6.2.5 仍待确认（与 D1a 解耦，都不阻塞实现）

| 编号 | 问题 | 状态 | 影响 |
| --- | --- | --- | --- |

### 6.3 已知边界（能力范围，不承诺）

- 不抗同机其他 Windows 用户读取——仅当 §6.2.3 的 ACL 收紧生效时才有用户隔离；ACL 失效（FAT/网络盘/被改权限）时没有。

## 8. 技术选型（D6 已确认：由我方定案）

> 本节结论为〔用户确认（m00354：技术栈由你定）→ 我方定案〕。**这是本次唯一由执行方代为决定的事项**；不再列候选表（v0.2 的四候选表已归档在 §13 的变更记录里）。

### 8.1 定案

**技术栈：.NET 10（LTS）+ WPF（Windows Presentation Foundation），C# 14，单进程桌面应用。**

| 维度 | 定案 | 理由 |
| --- | --- | --- |
| 运行时 | .NET 10 LTS | 〔事实〕2025-11 GA、支持至 2028-11；.NET 8 LTS 的支持窗口在本月（2026-11）到期〔推断：官方 LTS 三年节奏〕，新项目不应落在 EOL 上 |
| UI | WPF（`UseWPF`），不使用 WinUI 3 / MAUI / WebView | 贴边球、置顶、托盘、全局热键、per-monitor DPI 全是原生 Win32 能力，WPF 直接够得到；WinUI 3 需要额外打包复杂度（MSIX/WinAppSDK），MAUI 的 Windows 目标其实就是 WinUI |
| 语言 | C# 14，`<Nullable>enable</Nullable>`，`<TreatWarningsAsErrors>true</TreatWarningsAsErrors>` | 纯本地工具，编译期把空引用打干净收益远大于成本 |
| 形态 | 单进程、单 UI 线程、后台仅一个落盘任务 | 见 §8.6 |
| 发布 | `dotnet publish -r win-x64 -p:PublishSingleFile=true`，self-contained 与 framework-dependent 两种产物是否都出 | 具体取哪一种待 D7（安装形态）确认 |

### 8.2 为什么是这个（而不是另外三个）

我们的全部技术风险集中在四点：**贴边悬浮球的定位与显示、per-monitor DPI、置顶与焦点、托盘/热键的单实例行为**。这四点在 WPF 里都是"调用已有 API"，在 Web 壳（Tauri / Electron）里都是"自己写 Win32 绑定 + 处理 WebView2 的透明度与合成限制"。

- 对手是 **Tauri 2**：能省体积，但透明贴边窗 + 点击穿透 + 多屏 DPI 要写 Rust FFI；本项目只有三类功能，省下的体积换不来这部分工程风险。
- 对手是 **Electron**：TO-DO Panel 用 Electron 44 做到同类形态，代价是 `alwaysOnTop('screen-saver')` + 650 ms 折叠看门狗 + 60 ms 轮询鼠标位置（`main.js` 常量段）——为了补"原生窗口做不到的形变"而引入的复杂度，正好是我们不需要的。
- 对手是 **Flutter Desktop**：Windows 侧托盘/贴边生态最弱，且未来无跨平台需求（本工具明确只做 Windows，见 §1.3）。

可行性证据：PaperTodo v4.0.0-beta2 用 .NET 10 + WPF 实现了贴边胶囊队列、DirectComposition 预览、托盘、热键、MCP（`src/` 300 个 `.cs`、126,831 行）〔事实，见 `docs/PaperTodo_逆向分析_v1.0.md`〕。我们只取其中约 1/10 的形态复杂度。

反向证据（更值得记）：TO-DO Panel 的 ADR 0001 记录了一次"用 Swift 原生壳重写 macOS 壳"的尝试，最终因"原生壳只覆盖折叠态、主界面是 12,900 行渲染层"而回退〔事实〕。教训是**别为一个小形态引入双技术栈**——所以本方案坚持单一 WPF 实现，不搞"原生壳 + Web 正文"的混合。

### 8.3 工程结构

```
Win_Tool/
  Win_Tool.sln
  src/
    WinTool.App/                 # WinExe, net10.0-windows, UseWPF
      App.xaml(.cs)              # 启动、单实例、全局异常
      MainWindow.xaml(.cs)       # 三栏主界面（§3.2）
      Bubble/                    # 贴边悬浮球窗口 + 状态机（§3.3）
      Tray/                      # 托盘图标与菜单
      Settings/                  # 设置页
      app.manifest               # per-monitor v2（dpiAwareness=PerMonitorV2）
    WinTool.Core/                # net10.0, 不引用 WPF（可单测）
      Todos/                     # TodoItem、排序、完成策略
      Archive/                   # ArchiveService（§5.5 执行链）
      Notes/                     # 随笔模型与文件读写
      Credentials/               # 明文 JSON 实现 + ICredentialStore 接口（§6.2.2 第 5 条）
```

### 8.5 与选型相关的实现要点（可直接照做）

1. **悬浮球是一个独立 `Window`**：`WindowStyle=None`、`AllowsTransparency=true`、`ShowInTaskbar=false`、`ResizeMode=NoResize`、`Background=Transparent`；隐藏主窗口用 `Hide()`（不是 `Close()`），否则窗口状态与句柄都没了。
2. **贴边定位**：用 `SystemParameters.WorkArea`（当前屏工作区）或 `MonitorFromWindow` + `GetMonitorInfo`（多屏，D3d 待确认）；**不要**自己算任务栏高度——工作区已经扣掉了。
3. **DPI**：`app.manifest` 里 `PerMonitorV2`，窗口位置用 DIP 存、用 `DpiScale` 换算成像素再 `SetWindowPos`（PaperTodo 把 `DpiScale` 连同坐标一起持久化的做法可借鉴，`Models.cs:586-652`）。
4. **置顶**：`Topmost=true` 即可满足"球在最前"；**不要**用 TO-DO Panel 的 `setAlwaysOnTop(true,'screen-saver')` 提级（会与全屏应用/专注助手冲突，且其实际效果未验证）。
5. **全局热键**：`RegisterHotKey` + `HwndSource.AddHook`；必须处理 `1409`（已注册）并给出可见提示（PaperTodo `GlobalHotkeys.cs:795/892/1028`）。
6. **单实例**：`Mutex` + 命名管道转交参数（PaperTodo `SingleInstanceHelper.cs:22-105` 的结构可直接照搬）。
7. **开机自启**：写 `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\StartupApproved\Run`，不要裸写 `Run`（PaperTodo `SystemSettingsHelper.cs:9-63`）；默认开关待 D7。

### 8.6 已知代价与不做的优化

| 代价 | 处理 |
| --- | --- |
| WPF 视觉定制比 CSS 啰嗦 | 只做一套浅色/深色 + 少量圆角阴影，不追求 PaperTodo 级别的纸片拟物 |
| 冷启动耗时未实测〔未证实〕，不作承诺；WPF 的界面首次渲染成本高于纯文本壳 | 启动即显示托盘，主窗口按需创建（先可见性、后内容） |
| XAML 与代码双份维护 | 统一用 XAML 声明布局、代码只写行为；不学 PaperTodo 的全代码建界面 |
| 无法跨平台 | 明确非目标（§1.3） |

### 8.7 适用条件（这套选型成立的前提）

1. 只在 Windows 10 1809+ / Windows 11 上运行（`net10.0-windows` 目标即隐含此约束）。
2. 后续维护者接受 C#/XAML；若维护者只会前端，则本方案的 §5/§6/§7 逻辑仍成立，只需替换 §8.3 的 App 层为 Tauri 壳（Core 逻辑需重写为 TS，这是代价）。
3. 不要求绿色单文件分发以外的特殊形态（是否单文件见 D7）。
4. 不需要与 Web 服务端交互（本工具全离线；MCP/插件等 PaperTodo 能力不在范围内）。
